# Работа над ReLevel

- Перед задачей прочитай этот файл, соответствующие разделы [SPEC](docs/SPEC.md), [Tasks](TASKS.md) и существующий код.
- Выполняй задачу пользователя. Не меняй посторонний код и не расширяй объём работы без необходимости.
- При общей команде «продолжай разработку» бери первую незаблокированную задачу из TASKS.md. Закончи её реализацию и доступные проверки, затем сообщи результат.
- Существенные вопросы о поведении плагина согласовывай с пользователем. Обычные технические решения принимай самостоятельно.
- Пиши тезисно, но полными и понятными фразами. Не сокращай текст до потери смысла.

- SPEC описывает ожидаемое поведение, включая ещё не реализованное. Наличие требования не доказывает готовность функции.
- Не изменяй требования, чтобы оправдать ограничение или ошибку кода. Зафиксируй расхождение в TASKS.md.
- Не копируй требования целиком в TASKS.md. Укажи раздел SPEC, недостающую работу и критерий готовности.
- История изменений хранится в Git. Не добавляй в SPEC отчёты о проделанной работе и перечни исправленных ошибок.

# Ведение задач

- Статусы: «К выполнению», «В работе», «Проверить в Revit», «Готово», «Нужно решение».
- Перед работой переведи задачу в «В работе». После работы запиши результат и фактически выполненные проверки.
- Реализация завершена, но поведение в Revit не проверено → «Проверить в Revit».
- Сборка подтверждает компиляцию, но не правильность операций в Revit. Не отмечай задачу «Готово» только по успешной сборке.
- Результат ручной проверки принимай из собственного запуска Revit или сообщения пользователя. Указывай версию Revit и проверенные случаи.
- Если часть задачи осталась, сохрани её явно. Не объявляй весь механизм поддержанным по одному удачному примеру.
- При блокировке запиши конкретный вопрос или недостающие данные. Блокировка одной задачи не блокирует независимые задачи.

# Сборки

| Параметр | Основная | Legacy |
| --- | --- | --- |
| Линейка | `2025+` | `2024-` |
| Исходники | `src/ReLevel.Revit` | `legacy/src/ReLevel.Revit` |
| Среда | .NET 8 | .NET Framework 4.8 |
| Базовый API | Revit 2025 | Revit 2022 |
| Целевые версии | 2025–2026 | 2022–2024 |
| Конфигурация | Debug / Release | Legacy |
| Вывод | `bin/2025+` | `bin/2024-` |

- Проект, решение, манифест и документация общие. На каждую линейку выпускается одна `ReLevel.Revit.dll`.
- В выходной папке находятся `ReLevel.addin` и `ReLevel/ReLevel.Revit.dll`. DLL Revit API не включаются в поставку.
- Разработку плагина веди в основной версии. Legacy обновляй только по прямому запросу; обычная сборка не синхронизирует исходники.
- Не создавай в legacy отдельные проекты, решения, манифесты и копии документации.
- В `legacy/src/ReLevel.Revit/Compatibility` сохраняй адаптацию ID 32/64 бит и встроенных параметров.
- Совместимость проверяй в каждой заявляемой версии Revit. Успешная сборка против базового API её не гарантирует.

# Код

- `Logic/` — расчёты и результаты без Revit API.
- `Transfer/` — согласованные случаи переноса элементов, пересоздание видов, удаление, транзакции и проверки.
- `UI/` — окна WPF и действия пользователя.
- `Inspection/` — чтение диагностических данных элементов и запись снимков в ELEMENTS.md.
- `Localization/` — язык интерфейса и переводы.
- `ReLevelCommand.cs` — вход в команду; `Transfer/DeleteService.cs` — удаление элементов, видов и их зависимостей.
- Сохраняй небольшие классы с понятной ответственностью. Не дублируй расчёты и не скрывай исключения.
- Не добавляй отдельный Core и unit-тесты. Это не отменяет проверок результата внутри плагина и ручной проверки в Revit.

- Случаи обработки элементов описаны в SPEC. Новые случаи реализуй только после согласования требований с пользователем.
- В текущей разработке кейсов оставляй отбор объектов и алгоритмы переноса. Не добавляй проверки результата, снимки геометрии, сравнение параметров или контроль изменений других ID в рабочую операцию. Общую проверку для тестирования разрабатывать отдельно после всех кейсов. Обработка ошибок API и управление транзакциями остаются обязательными.

# Изменения модели

- Все изменения выполняй в транзакциях. Границы отката определяй до записи.
- Сбой регенерации считай критическим: прекрати обработку, безопасно откати операцию; не продолжай обычное чтение повреждённого состояния.
- Частичный результат пересоздания видов обрабатывай по SPEC. Не переноси эти послабления на удаление элементов и видов.

# Проверка и результат

- После изменения кода выполни `dotnet build ReLevel.sln -c Release` в среде с нужным SDK и Revit API.
- Если среда не позволяет выполнить сборку, укажи причину. Не подменяй отсутствующий запуск утверждением о готовности.
- Для изменений только в документах достаточно проверить согласованность, ссылки и отсутствие устаревших требований.
- Новый механизм проверяй на копии модели: успешная операция, неподдерживаемый случай, ошибка, сохранность зависимостей и Undo.
- Итог ответа: что изменено; что проверено; что осталось проверить; какой следующий шаг необходим.
