# Спецификация ReLevel

## 1. Обзор

ReLevel — плагин для Autodesk Revit 2025, предназначенный для изменения привязки элементов к уровню без изменения их физического положения в модели.

Плагин решает ситуации, когда элементы были созданы или привязаны к неправильному уровню, но уже правильно расположены в трёхмерном пространстве.

ReLevel изменяет логическую привязку к уровню, сохраняя положение элемента в модели.

## 2. Основной принцип

Основное требование:

> Изменение уровня, к которому привязан элемент, не должно изменять физическое положение элемента в модели.

Пример.

До переноса:

- отметка исходного уровня: 0 мм;
- смещение элемента: +1200 мм;
- абсолютная отметка элемента: +1200 мм.

Целевой уровень:

- отметка: +3000 мм.

После переноса:

- отметка целевого уровня: +3000 мм;
- смещение элемента: -1800 мм;
- абсолютная отметка элемента: +1200 мм.

Элемент физически остаётся на прежнем месте.

## 3. Поддерживаемые сценарии

ReLevel должен поддерживать два основных сценария работы.

### 3.1 Перенос выбранных элементов

Пользователь выбирает один или несколько элементов в Revit.

Пользователь запускает ReLevel.

ReLevel анализирует выбранные элементы и определяет, какие из них можно безопасно перенести.

Пользователь выбирает целевой уровень.

Поддерживаемые элементы переносятся с сохранением их положения в модели.

Выбранные элементы могут изначально принадлежать разным уровням.

### 3.2 Перенос элементов с уровня

Пользователь запускает ReLevel без необходимости предварительно выбирать элементы.

Пользователь выбирает:

- исходный уровень;
- целевой уровень.

ReLevel находит элементы, связанные с исходным уровнем.

Поддерживаемые элементы переносятся на целевой уровень с сохранением их положения в модели.

## 4. Поддержка элементов

Не все элементы Revit используют одинаковый механизм привязки к уровню.

ReLevel не должен предполагать, что для всех элементов достаточно изменить один универсальный параметр.

Элементы должны классифицироваться в зависимости от механизма их переноса.

Потенциальные группы:

- точечные элементы с привязкой к уровню;
- элементы на основе кривой;
- размещённые на хостах элементы;
- MEP-элементы;
- элементы с нижними и верхними ограничениями;
- другие особые случаи.

Точная классификация будет определяться в процессе разработки и тестирования.

Отдельная категория Revit не обязательно требует собственной реализации, если несколько категорий используют одинаковый механизм переноса.

## 5. Неподдерживаемые элементы

Если элемент нельзя безопасно перенести с использованием проверенной стратегии, ReLevel не должен его изменять.

Такой элемент должен быть классифицирован как неподдерживаемый.

Пользователь должен иметь возможность определить:

- какой элемент был пропущен;
- почему он был пропущен.

Неподдерживаемые элементы не должны препятствовать обработке поддерживаемых элементов, если продолжение операции не создаёт небезопасного или неконсистентного состояния модели.

## 6. Предварительный анализ

Перед изменением документа ReLevel должен проанализировать элементы, которые предполагается обработать.

В результате анализа элементы могут получить состояния:

- Ready — готов к переносу;
- Unsupported — не поддерживается;
- Cannot Change Level — уровень невозможно изменить;
- Invalid — некорректный элемент;
- другие состояния ошибок при необходимости.

До подтверждения операции пользователь должен примерно понимать, сколько элементов действительно будет обработано.

Пример:

Selected: 28

Ready: 24
Unsupported: 2
Cannot Change Level: 2

## 7. Пользовательский интерфейс

Интерфейс должен оставаться простым.

### Работа с выбранными элементами

Пример:

ReLevel

Выбрано:
15 элементов

Целевой уровень:
[ Level 03 ]

15 элементов готовы к переносу.

[ Отмена ] [ Перенести ]

### Работа со всем уровнем

Пример:

ReLevel

Исходный уровень:
[ Level 02 ]

Целевой уровень:
[ Level 03 ]

Найдено элементов:
247

[ Отмена ] [ Перенести ]

Точный дизайн интерфейса может изменяться в процессе разработки.

Опцию «Сохранять положение в модели» обычно не следует показывать пользователю, поскольку сохранение положения является определяющим поведением ReLevel.

## 8. Результат операции

После выполнения ReLevel должен показать сводку результатов.

Пример:

Перенесено: 231
Пропущено: 12
Ошибки: 4

Пользователь должен иметь возможность посмотреть подробную информацию о пропущенных элементах и ошибках.

Подробные результаты должны позволять определить соответствующий элемент и причину проблемы.

## 9. Проверка положения

Способ проверки сохранения положения зависит от типа элемента.

Для простого точечного элемента может быть достаточно проверить его Location.

Для других элементов могут потребоваться дополнительные проверки.

Потенциальные данные для проверки:

- `LocationPoint`;
- конечные точки `LocationCurve`;
- Bounding Box;
- соответствующая геометрия;
- параметры уровня;
- параметры смещения;
- координаты MEP-коннекторов;
- нижние и верхние ограничения;
- связи с хостами.

Механизм проверки не должен предполагать, что одно представление подходит для всех типов элементов.

## 10. Стратегия тестирования

Тестирование является одним из основных требований ReLevel.

### 10.1 Unit-тесты

Unit-тесты проверяют логику, для которой не требуется Revit.

Например:

- расчёт абсолютной отметки;
- расчёт нового смещения;
- сравнение положений с допустимой погрешностью;
- логика планирования и валидации переноса.

### 10.2 Интеграционные тесты Revit

Специальная тестовая модель Revit 2025 должна в дальнейшем содержать репрезентативные элементы для поддерживаемых механизмов переноса и категорий.

Тесты должны сохранять соответствующее состояние элемента до переноса, выполнять перенос и сравнивать полученное состояние.

Основной инвариант:

`PositionBefore ≈ PositionAfter`

Дополнительные инварианты должны проверяться там, где это необходимо.

Например:

- уровень изменён на целевой;
- смещения рассчитаны правильно;
- геометрия не изменилась;
- размеры не изменились;
- коннекторы остались в тех же координатах;
- необходимые соединения сохранились;
- связь с хостом осталась корректной.

Каждая стратегия переноса в дальнейшем должна иметь соответствующее интеграционное покрытие.

## 11. Тестовая модель

В дальнейшем должна быть создана специальная модель:

`test-models/ReLevel.TestModel.2025.rvt`

Она должна содержать контролируемые примеры поддерживаемых типов поведения элементов.

Тестовую модель следует рассматривать как часть инфраструктуры тестирования, а не как демонстрационный проект.

## 12. Обработка ошибок

ReLevel должен отдавать приоритет безопасности модели, а не максимальному количеству перенесённых элементов.

Операция не должна оставлять элемент в частично изменённом состоянии.

Неожиданные ошибки должны явно регистрироваться и сообщаться, а не игнорироваться.

По возможности ошибка обработки одного элемента не должна препятствовать обработке других независимых корректных элементов.

## 13. Начальная техническая конфигурация

Начальная целевая среда:

- Autodesk Revit 2025;
- C#;
- .NET 8;
- Revit API 2025;
- Windows.

Начальная структура решения:

ReLevel.sln

src/
- ReLevel.Core/
- ReLevel.Revit/

tests/
- ReLevel.Core.Tests/

docs/
- SPEC.md

test-models/

Инфраструктура интеграционных тестов Revit будет спроектирована отдельно после того, как станет понятна базовая архитектура переноса.

## 14. MVP

Первая пригодная для использования версия должна:

1. Запускаться в Revit 2025.
2. Принимать выбранные элементы либо элементы, связанные с выбранным исходным уровнем.
3. Позволять выбрать целевой уровень.
4. Определять, поддерживается ли каждый элемент.
5. Переносить поддерживаемые элементы.
6. Сохранять их физическое положение в модели.
7. Безопасно пропускать неподдерживаемые элементы.
8. Сообщать о перенесённых, пропущенных элементах и ошибках.

Поддержка всех категорий Revit не требуется для первой рабочей версии.

Корректная работа с меньшим количеством проверенных типов элементов предпочтительнее широкой, но ненадёжной поддержки.
